## Secrets posture

- No secret values exist in any of the three settings files or in `~/.claude/settings.json`
  (its `env` holds five `CLAUDE_CODE_*`/`ENABLE_TOOL_SEARCH` flags). The MCP allow-list
  names tools, not credentials. The settings.json problem is privacy/portability, not leakage.
- All API keys and tokens live in `~/.config/fnox/config.toml` (generated by the
  dotfiles secrets bootstrap, which is slated to own fnox; keychain/age/Doppler providers; ~60 secrets; profiles
  `codex_research`, `codex_publish`, `agentsview_recall`). `AGENTS.md:55` routes research
  through `fnox --config … --profile codex_research --no-defaults --no-daemon
  --non-interactive exec -- <command>`, the correct exec-scoped pattern. Installed fnox is
  1.39.0 (pinned at `~/.config/mise/config.toml:121`), the latest release (2026-10-06).
- Caveat 1: the global fnox `[env]` has env inheritance on (user decision 2026-08-02,
  recorded in dotfiles `.claude/rules/secrets-out-of-the-shell-env.md`), so every Claude
  Code session, subagent and MCP server inherits the whole secret set from the shell.
  1.39.0: `fnox exec` now strips every out-of-scope profile secret from the child, even
  unresolved ones, so the profile exec route is tighter; nothing in the repo relies on the
  old behaviour.
- Caveat 2: `mise-env-fnox` (`[env._] _.fnox-env`) stays disabled in the global mise config
  because of the runaway `fnox config-files` bug recorded in the global mise config comment
  (the tracking issue now belongs to the dotfiles project). 1.39.0
  adds the mechanism mise should use instead: `fnox env --json` (versioned document with
  set/files/remove/missing/leases; `--keys` resolves only named secrets; `--describe` lists
  injectable keys without resolving) and the read-only `fnox-client` crate that reads a
  running daemon's cache in one socket round trip. The daemon socket path and protocol (v6)
  changed: the first daemon-enabled command after the upgrade starts a fresh daemon with an
  empty cache; `fnox daemon clear` still reaches the old one until it idles out. The repo
  route uses `--no-daemon`, so it is unaffected.
