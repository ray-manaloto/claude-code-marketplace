## Authorization analysis

Claim under test: `claude-takeover.md:11` "the five-stage workflow (grill-with-docs → to-spec → to-tickets → implement-spec → retro) runs under the user's standing authorization (round-1 Q3) from mattpocock-skills 1.3.1", and `ticket-retro.md:7-8` "The skill disables automatic model invocation, so this standing user request is the invocation authority."

What the plugin's rules say:

1. `invocation.md:5`: user-invoked = "reachable **only by the human typing its name**". `:8`: "nothing but the human can fire it: no other skill can." `:22`: a precondition on a user-invoked skill is phrased "tell the user to run `/…`", "never as a Skill tool call". `D/implement:9`: "that is an instruction to you, not something the agent will do unprompted." `D/ask-matt:91`: SKILL.md beats any secondary description.
2. Nothing in `P` defines a "standing authorization", a delegated invocation, or an authority a user can grant a session to fire a user-invoked skill later. The mechanism is the harness (`disable-model-invocation: true`), and a user message cannot change frontmatter. Round-1 Q3 (`T:321`) was worded by the parent as "Your `/grill-with-docs` invocation is the authorization for all five stages … invoked natively from mattpocock-skills 1.3.1"; the user's "yes" accepted a premise that was false on two counts: `/grill-with-docs` had not been invoked by the harness (#7), and the four other skills cannot be invoked natively by the session at all.
3. What **is** allowed: the session may read any `SKILL.md` as text and follow it; the user may ask for that explicitly; D2 §2.14(b) is the honest framing ("file-guided", per named stage, recorded as such). The `retro` SKILL.md's steps are not secret; the repo may adopt them as its own procedure. What is **not** allowed: calling that "the invocation authority" for a user-invoked skill, counting a file-guided pass as the skill having "run", or letting a round-1 answer stand in for the per-stage human keystroke that the skill's whole invariant is built on (`invocation.md:8`).
4. The repo's own retro rule is independent of the skill and stronger in one direction (apply, don't just propose: `ticket-retro.md:26-31`, ADR 0001) and weaker in another (no human pick of candidates: `D/retro:35`, `S/retro:25`). Both can coexist only if the docs stop borrowing the skill's name for the repo's procedure. D2 §3.1 resolves it correctly: `retro-writer`/`retro:gate` per lane under repo rules; `/retro` per session, typed, proposing.

Correct recording (binding form, consistent with `skill-invocations.md:3-9` and D2 §2.14):

- `claude-takeover.md:11`: replace "runs under the user's standing authorization (round-1 Q3)" with "`to-spec`, `to-tickets`, `implement-spec` and `retro` were applied file-guided at the user's round-1 Q3 request; they have not been invoked. A stage counts as invoked only when the user types it; `skill-invocations.md` adds that row."
